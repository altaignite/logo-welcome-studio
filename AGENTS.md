- Signup creates a real Lovable Cloud account on signature; a database trigger on new users builds the profile, application, audit event and pending subscription from signup metadata so no client writes are needed.
- Admin access is a role in user_roles granted only by invitation: owners invite from Staff (inviteStaff, staff_invites, 7-day expiry, chosen level) and grant_admin_for_domain grants the role when the invited address confirms. An email domain never grants access. The /admin layout gates by has_role and RLS enforces it. The admin login never names the staff domain, has no self-registration and shows one generic error for every failure.
- Client IPs come only from Cloudflare's cf-connecting-ip (never X-Forwarded-For) for rate limits, sign-in records and the shared-IP check.
- Application status changes follow the transition map in src/lib/admin.ts, and every change or note is written to application_events as the audit log.
- Keep selectable plan data, finite service-hour allowances, subscription terms and input validation in the shared signup module with concrete tests, so selection, review, downloaded agreements and completion use the same chosen plan.
- Use libphonenumber-js metadata for countries and dial codes; optional browser IP preselection must not overwrite manual choices or block signup.
- Treat displayed signature codes as local confirmation only, generated with Web Crypto and never reused within the current application, not as identity verification.
- Signup is a single centred column on every screen size (no photo panel), with minimal boxes: plain headings and dividers, cards only for plan choice.
- Agreement wording, operator details (Lanex Group, LLC), the client details table and the markup parser (headings, "|" tables, "!" notices) live in src/lib/agreements.ts (agreementDocuments(plan, client, date)); the on-screen reader (AgreementText) and the PDF (downloadAgreementPdf in src/lib/agreement-pdf.ts, logo letterhead) render the same blocks. Have agreement changes reviewed by counsel.
- Every order uses the same flow components in src/components/order-flow.tsx (PlanCards, review, AgreementsList, SignDialog): signup, /dashboard/order (client signs; orderAdditionalPlan records signed_at) and /admin/order/$userId (staff place it; client accepts by paying). No stepper bars.
- Every new plan starts its Stripe subscription immediately (startStripeSubscription in src/lib/billing.server.ts) with payment_settings.save_default_payment_method=on_subscription, so the card that pays the first invoice is saved and every renewal is charged automatically, as the agreement says. Client self-serve orders and auto-approved signups use charge_automatically + default_incomplete (paid in PayStep; Stripe expires an unpaid first invoice after about 23 hours and the order is cancelled); staff orders and staff-approved signups use send_invoice due in 7 days and switch to charge_automatically on activation once the card is saved. The subscription's first invoice (billing_reason subscription_create, metadata kind first) activates the plan when paid. Don't create standalone first invoices with issueStripeInvoice.
- Payment cards live in src/lib/cards.server.ts (pure rules in src/lib/cards.ts with tests) behind src/lib/cards.functions.ts, with the UI in src/components/payment-cards.tsx. Clients (Invoices page) list cards, add one through Stripe's SetupIntent form (saved off_session and made the default), make a card the default (setDefaultCard: customer default plus every running subscription via applyDefaultCard) or remove one (a card paying for plans moves them to the next card first, and is refused if it's the only card). Every "Pay now" opens PayInvoiceButton: pay with a saved card or a new one (saved first, then charged), confirmed in the browser so 3-D Secure works; Stripe's hosted page stays as a fallback. Staff with the billing permission get the account's Payment cards tab: list, make default, remove, ask the client for a new card (notification) and charge a saved card for an open invoice (chargeInvoice: off_session, idempotent per minute, audited; when the bank wants the cardholder to confirm, the client is notified to pay). Staff never type card numbers. Payments are still recorded only by the signed webhook. The card-only customer portal (billingPortal, cardPortalConfiguration) remains available but isn't linked; never open a portal session without that configuration, because Stripe's default portal allows cancelling. The signed customer.updated webhook copies a new customer default card onto running subscriptions.
- Client orders end with PayStep (src/components/pay-step.tsx): Stripe's Payment Element pays the order's first invoice in the page, using the invoice's confirmation secret from invoicePayment (src/lib/billing.server.ts; owner-only, live from Stripe) via /api/public/signup-payment during signup or invoicePaymentDetails when signed in. The browser only shows success; the invoice is marked paid by the signed webhook. Flagged signups get no pay step (staff review first). Payment comes after signing because NY auto-renewal law needs consent to the renewal terms before the charge. Needs Stripe's publishable key (STRIPE_PUBLISHABLE_KEY secret or app_secrets stripe_publishable_key); without it, or if Stripe.js is blocked, the step links to Stripe's hosted invoice page. CSP, Permissions-Policy (payment) and COOP (allow popups) allow Stripe in src/server.ts.
- Render country flags from the free FlagCDN image API with empty alt text alongside country names and graceful image-failure fallback, so flags remain decorative rather than replacing accessible country labels.

- After every code or database change, do a focused security-audit-skill review (guidance mode) of the changed trust boundaries before finishing; the owner requires security checks on every change.
- Admin record pages are one generic route (/admin/records/$kind/$id) driven by src/lib/records.ts; add a record type there instead of writing a new page, so every table row opens a consistent details page.
- Financial and legal records (applications, subscriptions, invoices, transactions, audit) are archived or voided, never deleted; only tables listed in deletableTables in src/lib/admin.ts get DELETE policies.
- Stripe is called through the fetch-based client in src/lib/stripe.server.ts (Worker compatible, no SDK; key from STRIPE_SECRET_KEY, or the older STRIPE_RESTRICTED_API_KEY); orders check Stripe before creating local rows and cancel them if the invoice fails; Billing rules shows the Stripe setup check; billing workflows live in src/lib/billing.server.ts and pure rules in src/lib/billing.ts with tests, so the webhook, cron and server functions share one implementation.
- Local invoices and transactions mirror Stripe: the signed webhook at /api/public/stripe/webhook (idempotent via stripe_events), the daily reconcileStripe and the Stripe import (src/lib/stripe-import.server.ts) all record payments through recordInvoicePaid from verified Stripe data; never mark invoices paid from the UI.
- Interest and fees accrue in invoice_charges via the daily /api/public/cron/collections job and are billed to Stripe only when staff issue an arrears invoice, to avoid sweeping them into subscription renewals.
- Staff write access follows staff levels (owner, manager, support, billing, viewer) in src/lib/staff.ts, mirrored by public.level_grants and enforced by has_perm in RLS; every staff server function calls requirePerm from src/lib/access.server.ts because service-role writes bypass RLS. New staff start as viewers.
- Server functions use requireSession (src/lib/session.middleware.ts), never requireSupabaseAuth directly, so a session that hasn't passed its two-factor code is refused; every RLS table also carries the restrictive "two-factor session" policy (a test checks new tables).
- Notifications are written by database triggers via public.notify / notify_staff (links are in-app paths only) and emailed by the /api/public/cron/notifications job (schedule every 10 minutes; needs RESEND_API_KEY and EMAIL_FROM, optional APP_URL). Don't send email from feature code.
- Client files live in the private client-files bucket under the client's own folder; uploads and downloads go only through startFileUpload, finishFileUpload and fileLink (short-lived signed URLs), never direct storage access.
- Application events moving into a client-facing status (clientVisibleStatuses in src/lib/admin.ts) are shared with the client, note included; staff can't share anything else on the timeline.
- Signed agreements are rendered server-side from agreementDocuments in src/lib/agreements.ts and stored once, immutably, in signed_agreements; bump AGREEMENT_VERSION when the wording changes.
- Only the client decides on a deliverable (reviewDeliverable); staff send for review, withdraw or archive.
- Privacy requests are fulfilled with fulfilAccessRequest (export to the client's Documents) and fulfilDeletionRequest (anonymise and block sign-in, keeping financial and legal records).
- Account status changes go only through setAccountStatus: suspended/closed ban sign-in and end every session (revoke_user_sessions), on hold/suspended pause plans in Stripe (marked paused_by_account_status so reactivation resumes them), cancelled/closed cancel them; the restrictive "active account" policy and requireSession lock suspended and closed accounts out immediately (a test checks new tables).
- Clients never write tables directly: tickets, replies, uploads, reviews and requests go through server functions with validation and rate limits.
- Disposable email domains live in src/lib/disposable-domains.ts and are seeded into blocked_email_domains; handle_new_user and sync_profile_email refuse them on the server.
- Sign-ins are recorded once per session by requireSession (sign_in_events, Cloudflare location headers); a new location notifies the account's staff and the user.
- Subscriptions and invoices follow Stripe's live status through syncSubscriptionFromStripe (webhook and the daily reconcileStripe in /api/public/cron/collections); payments are recorded only from verified Stripe data (webhook or Stripe API). Staff can import all Stripe customers, subscriptions and invoices and force a sync from Billing rules; the admin shows a banner when a migration is missing (schemaStatus).
- Money-back guarantee rules are guaranteeCheck in src/lib/billing.ts: request after 90 days, within the next 30, no failed or late invoices, not voided, no sales.
- The client-files bucket is created on first use by ensureBucket (Lovable Cloud migrations can't create storage buckets).
- Errors: show them with ErrorState (inline, with retry) or an error popup, and use friendlyError for wording; every error popup, failed query or save, route error and unhandled rejection is reported to Lovable through reportError (src/lib/errors.ts).
- Loading: use PageSkeleton, TableSkeleton, SectionSkeleton, Spinner and AppLoader from src/components/loading.tsx, never "Loading…" text; TopProgress shows any navigation, fetch or save.
- Protected layouts use guardClient / guardStaff (src/lib/session-guard.ts): local session, cached staff check, background sign-in check. Don't add network calls to layout beforeLoad.
- Every admin list (/admin/records/$kind) creates records through the client picker; invoices and subscriptions go through Stripe server functions, and Stripe-mirrored transactions can't be created by hand.
- A subscription's status follows its invoices through applySubscriptionStanding (rules in subscriptionStanding, src/lib/billing.ts): nothing late is active (invoices not yet due change nothing), late or failed is past due, debt recovery/legal/court or Stripe "unpaid" is suspended (Stripe collection paused, projects on hold, application suspended), and a new order whose first invoice is voided is cancelled. Call it after any invoice change; the daily sync re-checks every plan.
- Rate limits: every server function uses limited("<name>") from src/lib/session.middleware.ts with a rule in src/lib/limits.ts (a test checks every function), on top of the per-user request limit in requireSession; counts live in rate_limit_hits via hit_rate_limit (service role only).
- Buttons are black (Button default variant and .signup-primary, including hover); red is only for destructive actions. Text actions use foreground with underline, not the red brand colour.
- Mobile numbers are stored and validated in international format; the input next to the dial-code picker shows only the national part (phoneNational in src/lib/signup.ts), so the dial code appears once.
- Clients sign one plain-language Service Agreement (parties and plan tables, the automatic-renewal notice NY law requires, key terms in one paragraph) that incorporates the full policies at https://firstpersonmarketing.com/legal (LEGAL_URL) by reference; the marketing site and its legal pages are separate from this platform. Keep the paragraph in step with the real rules (billing, cancellation, guarantee, interest cap).
- One account per client, many plans, without leaving signup: after the plan, signup asks for the email and checks it with /api/public/account-check (yes/no only, rate limited per IP and per email via accountCheck limits). Existing accounts sign in inline (password, forgot-password email, two-factor) and continue in ExistingClientOrder (OrderWizard + orderAdditionalPlan); new emails continue to details and create a password. A signed-in visitor goes straight to ExistingClientOrder.
- Security flags restrict accounts to "Fraud - KYC" only through public.flag_for_kyc (database) and flagForKyc (src/lib/kyc.server.ts): status and reason, urgent Security ticket with an internal note, staff alert, audit, and plans paused via applyAccountStatusEffects (src/lib/account-status.server.ts, shared with setAccountStatus). Restricting patterns: Stripe early fraud warnings and chargebacks (webhook) and a disposable or undeliverable email found on first sign-in. Softer signals only open a Security review ticket and alert staff via public.flag_for_review / flagForReview, without restricting: a mobile number shared with another account (profiles trigger, re-checked on orders) and 3+ new accounts from one IP in 24 hours (recordSignIn). Restricted clients can sign in but RLS and requireSession refuse everything; they see /kyc (identity and residence proof to kyc@firstpersonmarketing.com). Staff reinstate by setting the account to Active.
- Unconfirmed emails: sign-in on the login page, admin login and the signup sign-in step shows unconfirmedPopup (src/lib/email-confirmation.ts) with a resend action; the signup confirmation screen offers a resend link with a 60-second cooldown.
- Never trust the browser: signup details are validated again in handle_new_user (names, business, country, international mobile, plan), profile edits must keep a valid mobile number, orders need a complete profile, and signed-out visitors have no table privileges at all (0021; new tables included by default privileges). Browser code is public by nature: keep secrets, prices and rules on the server; production builds ship no source maps.
- Security headers live in src/server.ts. The enforced CSP covers object-src, base-uri, frame-ancestors, form-action and upgrade-insecure-requests; the full allow-list runs as Content-Security-Policy-Report-Only until it shows no violations on the published site.
- Security log: server code records blocked or suspicious activity with logSecurityEvent (src/lib/security-log.server.ts → public.log_security_event), grouped per kind, source and hour (never one row per request). Sources: rate limits, fake Stripe webhooks, unauthorised cron calls, staff permission refusals and non-staff calling staff actions, restricted-account activity, KYC restrictions (trigger), staff data exports, privacy exports, CSP reports (/api/public/csp-report) and server errors. High/critical events alert owners. Owners see it at /admin/security with guidance from src/lib/security-guide.ts (add a guide entry for any new kind; a test checks). Kept 180 days.
- Passwords: one policy in src/lib/passwords.ts (8+ characters, letters and numbers, no repeats or simple sequences, not built from the own email; no symbol or case rules) plus a Have I Been Pwned k-anonymity check (only a 5-character hash prefix leaves the browser) on signup, password reset and password change. Also turn on Supabase leaked-password protection.
- Email risk: src/lib/email-risk.ts (syntax, disposable, role, random-looking, typo suggestions, spam-prone endings) and email-risk.server.ts (MX via Cloudflare DNS-over-HTTPS, domain age via RDAP, staff block list). Blocked: invalid, disposable, undeliverable. Review (allowed, logged as email_high_risk): domains under 30 days old (new businesses often have new domains) and other signals. Checked at the signup email step and again on each account's first sign-in (blocked ones are restricted for KYC). Lookups failing never block.
- Cancellations, upgrades, downgrades and account closures are signed applications in the signup style (/dashboard/change/$id, /dashboard/close via src/components/change-flow.tsx and src/lib/changes.functions.ts), actioned immediately and stored in account_change_requests for staff review (Change requests in the admin; read-only, Mark reviewed). Started plans are never cancelled immediately, by anyone: they cancel at period end in Stripe (cancelNowAllowed only allows unpaid new orders). Closing an account cancels every plan at period end, keeps invoices payable and sets the status to closed (never deleted), banning sign-in and ending sessions.
- Interest is capped at New York's civil usury limit: NY_MAX_MONTHLY_INTEREST_PCT (1.24% a month compounded ≈ 15.9% a year) in src/lib/billing.ts, enforced by a billing_settings check constraint (0024) and cappedInterestPct in collections.
- Stripe: the live endpoint https://logo-welcome-studio.lovable.app/api/public/stripe/webhook is limited to requiredStripeEvents; the preview-domain duplicate is disabled. Other endpoints in the Stripe account belong to other projects.
- Signup progress is saved in this browser (src/lib/signup-draft.ts, 7 days; plan, email, details, mobile, account number and step, never passwords or signature codes). Returning visitors are offered Continue or Start over; past the details step they resume at "create your password", existing clients at sign-in. Cleared when signup or the order completes.
- Clean signups are approved automatically right after signing (/api/public/signup-payment: account id + email, created in the last 30 minutes, rate limited, email risk re-checked on the server) and otherwise on the first sign-in (autoApproveSignup in src/lib/billing.server.ts, called last in recordSignIn): email risk "ok", no open Security ticket, not restricted, application still submitted. It approves, logs "Approved automatically" and sends the first invoice (sendFirstInvoiceFor); paying it is then the last step of signup, after signing (review → agreements → sign → pay → done). Unpaid first invoices get client reminders after 2 and 5 days and a billing staff alert after 7 (runDailyReminders). Anything flagged waits for staff.
- Plans show "A typical month" (typicalMonth in src/lib/signup.ts) so they read as results, not just hours; these are examples, not commitments.
- CI (.github/workflows/ci.yml) runs typecheck, lint (errors fail; any is a warning to shrink), tests and build on every push; keep it green. Formatting is not enforced by lint; prettier stays available as `npm run format`.
- SECURITY DEFINER functions bypass RLS, so the restrictive two-factor and active-account policies do not protect them: staff-only ones must check has_perm (or has_role) and mfa_session_ok themselves, internal ones are granted to service_role only, and trigger functions are revoked from PUBLIC (0027).
- Request guards in src/server.ts run before the app: plain HTTP on the public site is redirected to HTTPS (308; HSTS keeps browsers there), and any non-GET request whose browser Origin header names another host is refused with 403 and logged as cross_site_request (Stripe's webhook is exempt; server-to-server calls send no Origin). Auth uses bearer tokens, not cookies, so forged requests carry no credentials anyway. Tests in src/test/request-guards.test.ts.
- Password reset links work for one hour: /reset-password only accepts a session created by a recovery link in the last 60 minutes (recoveryAllowed in src/lib/passwords.ts, tested); a normal signed-in session can't set a password there (the Security page needs the current password). Keep Supabase's email link expiry at 1 hour or less.
- The client-files bucket enforces the size and type limits itself (ensureBucket re-applies them if they drift); never allow text/html or image/svg+xml.
- Dependabot (.github/dependabot.yml) opens weekly grouped updates and security PRs for bun packages and GitHub Actions; CI must pass before merging. Validation uses zod 4.
